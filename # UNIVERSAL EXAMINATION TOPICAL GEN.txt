# UNIVERSAL EXAMINATION TOPICAL GENERATOR

## From-Scratch, Multi-Board, Multi-Format, 2001 → Future-Proof Architecture

---

## 0. PRIMARY OBJECTIVE

Build a production-grade examination question extraction and topical classification system completely from scratch.

The system must support, as first-class examination ecosystems:

1. Cambridge International / CAIE
    
2. SAT / College Board
    
3. International Baccalaureate / IB
    
4. AQA
    
5. Pearson Edexcel
    

The architecture MUST also allow additional examination boards to be added without rewriting the extraction engine.

The system must work with examination materials dating from approximately 2001 onward and must remain usable for future examination years without requiring hardcoded year-specific logic.

Do NOT build a "Cambridge generator with extra board support."

Build a:

> **Universal Examination Document Intelligence Engine**

Cambridge, SAT, IB, AQA and Edexcel are adapters/plugins on top of the same core engine.

---

# 1. NON-NEGOTIABLE DESIGN PRINCIPLES

## 1.1 No hardcoded "current year"

Never assume:

```text
2024
2025
2026
```

or any other fixed year.

The parser must accept:

```text
1900–9999
```

where appropriate and preserve unknown/future years.

The system must continue working with:

```text
2001
2002
...
2026
2027
...
2030
...
2099
```

without code modification.

If a filename contains an unfamiliar year, the year parser must still attempt to identify it.

---

## 1.2 No board-specific assumptions in the core engine

The core engine must not contain logic such as:

```python
if board == "CAIE":
    ...
elif board == "AQA":
    ...
elif board == "Edexcel":
    ...
```

throughout the codebase.

Instead:

```text
core/
    document.py
    page_analysis.py
    question_detection.py
    crop_engine.py
    assembly.py
    classification.py
    validation.py

adapters/
    caie/
    aqa/
    edexcel/
    ib/
    sat/
```

Each board adapter translates its own documents into a universal internal representation.

# 4. QUESTION TYPES

Question detection must not depend on Cambridge-style numbering.

Supported question structures must include:

### MCQ

```text
1.
A ...
B ...
C ...
D ...
```

and:

```text
Question 1
...
A
B
C
D
```

and compact answer grids.

---

### Structured

```text
1(a)
1(b)
1(c)(i)
1(c)(ii)
```

---

### Essay

```text
Discuss...
Evaluate...
To what extent...
Explain...
```

including large answer spaces and questions without obvious `[marks]`.

---

### Source-based

```text
Read Source A...
Using the source...
Study the extract...
```

---

### Data-response

Tables, graphs, figures, datasets and multi-part questions.

---

### Case study

A stimulus followed by several numbered questions.

---

### Practical / experimental

Must preserve:

- apparatus diagrams
    
- tables
    
- graphs
    
- experimental setup
    
- observations
    
- calculations
    
- method questions
    

---

### Multi-page question

A question may start:

```text
Page 1
```

continue:

```text
Page 2
Page 3
```

and finish several pages later.

The system must recognize this as ONE question.

---

### Split question

Example:

```text
Question 4
...
```

followed by another question on the same page.

The crop engine must split them correctly.

---

### Unnumbered questions

Some examination formats may use headings or prompts instead of conventional numeric markers.

The engine must support structural detection rather than requiring a number.

# 9. BARCODE DETECTION

Barcode removal is mandatory.

The crop engine must detect:

```text
1D barcodes
2D codes
QR-like structures
candidate identification blocks
registration marks
black administrative blocks
vertical barcode strips
horizontal barcode strips
```

Detection must combine:

```text
connected-component analysis
+
projection profiles
+
repeated vertical-line patterns
+
PDF vector analysis
+
OCR/text location
```

Never simply crop a fixed number of pixels from the top.

A barcode can occur:

```text
top
bottom
left
right
inside an administrative margin
```

Therefore barcode removal must be spatially independent.

---

# 10. HEADER / FOOTER DETECTION

Detect repeated content across pages.

For each page:

```text
header fingerprint
footer fingerprint
left-margin fingerprint
right-margin fingerprint
```

If a region repeats across multiple pages and contains:

- candidate number
    
- centre number
    
- barcode
    
- copyright
    
- page number
    
- board branding
    
- administrative identifiers
    

classify it as non-question structural material.

BUT:

Never remove a region simply because it repeats.

For example:

```text
Question 3
```

may repeat naturally as a continuation header.

Therefore the classifier must determine whether the region is:

```text
administrative
or
content-bearing
```

# 11. BLANK PAGE DETECTION

Create a dedicated:

```text
blank_page_detector.py
```

A page is not considered blank merely because it has little text.

Check:

```text

PDF drawings
images
vector objects
OCR
large whitespace regions
```

Recognize:

```text

This page is intentionally blank
Turn over
Continue...
```

BUT:

Do NOT remove a question page containing:

- a large graph
    
- a diagram
    
- a table
    
- a map
    
- a chemistry structure
    
- an apparatus
    
- a large answer space
    

A page with little text can still contain important examination content.

# 12. CROP ENGINE — ABSOLUTE REQUIREMENT

Final question image:

```text
WIDTH = 2280 PX
```

Always.

No exceptions.

---

# 13. TOP CROP ALGORITHM

Do NOT use:

```python
start_px - 5
```

Do NOT use a fixed proportional margin.

Do NOT blindly crop the page from the question number.

Instead:

### Step 1

Locate the question marker.

### Step 2

Find its complete first content line.

### Step 3

Look upward for:

- superscripts
    
- fraction numerators
    
- mathematical notation
    
- chemical structures
    
- continuation text
    
- labels
    
- diagrams attached to the question
    

### Step 4

Determine:

```text
first_content_ink_y
```

### Step 5

Set:

```text
crop_top = first_content_ink_y - 20
```

---

# 14. FINAL RASTER AUTHORITY

The PDF coordinate estimate is NOT the final authority.

After rendering:

```text
render
→ crop
→ assemble
→ resize
→ raster scan
→ locate first ink
→ re-anchor
```

The final image must contain:

```text
EXACTLY 20 PX OF VERIFIED WHITE
ABOVE THE FIRST QUESTION INK
```

unless the physical page boundary prevents it.

If fewer than 20 pixels exist:

```text
pad with verified white pixels
```

If more exist:

```text
remove only verified-white rows
```

Never remove ink.

---

# 15. ZERO TOP-CLIPPING SYSTEM

Before saving every crop:

```python
assert first_ink_y >= 20
```

Then verify the first 20 rows.

They must contain no meaningful ink.

Then inspect the first content region using:

```text
OCR
connected components
PDF text boxes
```

If text appears clipped:

```text
REJECT CROP
RECALCULATE
RENDER AGAIN
```

Never silently save a questionable crop.

# 23. TOPIC CLASSIFICATION

This is where the biggest improvement should happen.

Do NOT rely on keyword matching alone.

Use a layered classifier.

## Layer 1 — exact taxonomy terms

Match syllabus-defined concepts.

## Layer 2 — semantic concepts

Recognize equivalent terminology.

Example:

```text
rate equation
rate law
reaction rate expression
```

can map to the same concept.

## Layer 3 — mathematical/formula recognition

Detect:

```text
equations
symbols
units
chemical formulae
graphs
statistical expressions
```

## Layer 4 — question intent

Identify:

```text
calculate
explain
evaluate
compare
analyse
describe
determine
prove
show that
```

## Layer 5 — contextual evidence

Understand what the question is actually asking.

This audit is mandatory before major implementation begins.# 84. INDEPENDENT MULTI-SIGNAL VALIDATION ARCHITECTURE

The system must be designed around a critical principle:

> **Never make an important extraction decision using a single detection method when an independent second signal can validate it.**

The goal is not to make the system "better at guessing."

The goal is to make the system **structurally incapable of silently accepting an uncertain or contradictory result.**

For important decisions, use at least two materially different signals/approaches wherever practical.

Examples:

```text
PDF text/layout analysis
+
raster/visual analysis
```

```text
question-number detection
+
question-content/answer-choice detection
```

```text
PDF coordinate analysis
+
final-raster ink analysis
```

```text
question-paper structure
+
mark-scheme structure
```

```text
metadata identity
+
text similarity
+
image similarity
```

If independent detectors agree:

```text
Detector A: Q17 ends at Y=1432
Detector B: Q17 ends at Y=1431
                    ↓
              HIGH CONFIDENCE
```

the system may automatically accept the result if all other validation checks pass.

If they disagree materially:

```text
Detector A: Q17 ends at Y=1432
Detector B: Q17 ends at Y=1478
                    ↓
             REVIEW_REQUIRED
```

Do NOT:

```text
average the coordinates
pick whichever looks convenient
use the higher confidence score
silently choose one
```

The disagreement itself is evidence of uncertainty.

Therefore:

```text
AGREEMENT → automatic validation may proceed
DISAGREEMENT → investigate/reprocess/review
```

This principle must apply throughout the system wherever independent validation is possible.

ONE EXTRACTED QUESTION = ONE COMPLETE IMAGE.

The system must never produce:

```
half a question
```

or:

```
question + neighboring question
```

in the same SAT question image.

The final crop must contain exactly one logical SAT question.

This invariant must be tested aggressively.

Test:

- one question per page
    
- two questions per page
    
- three or more compact questions per page
    
- passage questions
    
- graph questions
    
- table questions
    
- equations
    
- diagrams
    
- questions near page footers
    
- questions near page headers
    
- questions adjacent to page boundaries
    
- unusually large questions
    
- unusually small questions
    
- dense layouts

# FIX: UNIVERSAL EXAM DOCUMENT TYPE & BOARD DETECTION

`9701_s24_qp_42.pdf`

# FINAL INSTRUCTION

Do not treat this as a simple feature addition.

Treat the existing Universal Cambridge Topical Generator as the foundation of a **structured Cambridge question-bank intelligence platform**.

Before coding:

1. Inspect the existing architecture.
    
2. Identify what already exists.
    
3. Research the relevant Cambridge syllabus/component structures.
    
4. Design the intelligence layer around the existing metadata.
    
5. Reuse existing functionality wherever possible.
    
6. Implement incrementally.
    
7. Test every new subsystem.
    
8. Preserve backward compatibility.
    
9. Optimize for large datasets.
    
10. Never fabricate missing information.
    

The final system should not merely answer:

> “What topic is this question?”

It should be capable of understanding:

> **What is this question, where did it come from, what syllabus concepts does it test, what skills does it require, how difficult is it likely to be, what other questions resemble it, how well represented is this concept in the dataset, and how can it be intelligently selected for a custom revision set or booklet?**

### REAL SOURCE PAPER / EVIDENCE REQUIREMENT

For any research, validation, classification, topic mapping, component analysis, syllabus mapping, question-pattern analysis, or other task where the system needs evidence of how Cambridge actually structures or assesses something:

**USE REAL CAMBRIDGE PAPERS AND OFFICIAL CAMBRIDGE MATERIALS. DO NOT GENERATE FICTIONAL OR SYNTHETIC PAPERS.**

The system must:

1. Prefer **real Cambridge past papers** from the relevant:
    
    - syllabus
        
    - syllabus/version
        
    - qualification
        
    - year
        
    - session
        
    - component/paper
        
    - variant where applicable
        
2. Use real:
    
    - Question Papers (QP)
        
    - Mark Schemes (MS)
        
    - Examiner Reports (ER)
        
    - Inserts
        
    - Specimen papers
        
    - Syllabus documents
        
    - Official Cambridge assessment/materials
        
3. When investigating a paper/component/topic, inspect the **actual source documents** rather than relying solely on:
    
    - generated examples
        
    - assumed question structures
        
    - generic LLM knowledge
        
    - synthetic questions
        
    - guessed Cambridge conventions
        
4. If a real paper exists, it must take precedence over a generated example.
    
5. If the system needs an example question for testing an algorithm, clearly distinguish:
    
    - `REAL_SOURCE_QUESTION`
        
    - `SYNTHETIC_TEST_QUESTION`
        
    
    Synthetic questions must **never** be presented as genuine Cambridge questions.
    
6. Every factual claim derived from a Cambridge paper should retain provenance, including where practical:
    
    - syllabus
        
    - year
        
    - session
        
    - component
        
    - variant
        
    - paper filename
        
    - page number
        
    - question number
        
7. For structural research, sample **multiple real papers across years/sessions/variants** where available instead of basing conclusions on one paper.
    
8. When analyzing component structure, question types, topic distribution, command words, marks, difficulty patterns, or recurring question structures, derive the information from the **actual papers and mark schemes**.
    
9. When a real source cannot be found or accessed, the system must explicitly report:  
    `SOURCE_NOT_FOUND`  
    or  
    `SOURCE_NOT_ACCESSIBLE`
    
    It must **not fabricate the missing evidence**.
    
10. The system must never create a fake Cambridge paper, fake question number, fake mark scheme, fake examiner comment, or fake historical assessment structure and represent it as authentic.
    

### SOURCE-FIRST RESEARCH PIPELINE

Whenever research is required:

`Official Cambridge Source → Real Paper → Extract → Analyse → Store Evidence → Use in System`

NOT:

`LLM Assumption → Generate Example → Treat Example as Cambridge Evidence`

Generated/synthetic material may only be used for **internal software testing**, and must always be explicitly labelled synthetic.

### PAPER RESEARCH DEPTH

For important structural decisions, the research engine should attempt to inspect a representative collection of real papers, for example:

- multiple years
    
- multiple sessions
    
- multiple variants
    
- multiple components
    
- old and new syllabus versions where relevant
    

The exact sample size should depend on availability.

The purpose is to prevent the system from incorrectly generalizing from a single paper.
